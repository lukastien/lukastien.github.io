01 — PROJECT OVERVIEW

The problem & the solution

Community loan closets, schools, and non-profits lend shared equipment — wheelchairs, medical and educational gear — often tracked on paper logs or a single spreadsheet. The failure modes are familiar: lost or overdue inventory with no reminder trigger, double-bookings because availability isn't live, and volunteers burning out on manual follow-up.

Mobility Loan Closet (the Loan Closet Tracker) digitises the whole checkout loop: an AppSheet app for checkout/return, a Google Sheets relational database, automation that emails borrowers, and an Apps Script integration that posts loan events to an external API endpoint.

Built for the people who actually run these closets — volunteers and coordinators — so it is deliberately low-code: no server to maintain, works on phone and desktop, and every checkout updates availability in real time.

Relational schema (3 tables)

Equipment (EquipmentID, name, category, condition, status), Borrowers (BorrowerID, name, email, phone), and Loans (LoanID, EquipmentID → Equipment, BorrowerID → Borrowers, loan/return dates, status) — proper reference keys in Sheets, keyed with UNIQUEID().

Live availability

AppSheet data slices with conditional expressions (e.g. [Status] = "Available") so the catalogue only shows what can actually be lent — attacking double-booking at the UI layer.

Automation

An event-driven AppSheet bot watches for checkout/return conditions and branches into a dynamic HTML email confirmation and an Apps Script webhook task.

API integration

sendLoanToAPI() in Google Apps Script packages loan data as JSON and POSTs it via UrlFetchApp.fetch with error handling (muteHttpExceptions + try/catch) — demonstrating how the closet can sync to an external CRM (e.g. HubSpot-style) endpoint.

The API endpoint in the published code is a mock/example endpoint demonstrating the integration pattern — the payload shape, POST mechanics, and error handling are real; no production CRM is connected.

03 — CHALLENGES & DECISIONS

Challenges & decisions

Relational discipline in a spreadsheet

Challenge: Sheets invites one giant table, which would tangle inventory, people, and loan history together.

Decision: Model three normalised tables with reference keys, mirroring how the same system would be designed in SQL — the low-code tool does not excuse a flat data model.

Volunteer-proof UX

Challenge: If checkout takes more than a few taps, staff revert to paper and the data rots.

Decision: Put availability filtering (slices) and one-tap status changes in the app, and let automations — not humans — send confirmations and sync records.

Proving external sync without a real CRM

Challenge: There is no production CRM to integrate against for a community project.

Decision: Build the full JSON POST path against a mock endpoint with production-style error handling, and label it as a demonstration in the repo.
